# ThinkRider V100 — current evidence

## 2026-10-17 live identification (observed)

Linux, BlueZ 5.87, adapter hci0. Raw captures are not published.

- No V100 was found in the 2026-10-16 scans. It appeared on 2026-10-17 while the tester was pressing its buttons, advertising as **`Think VS01-XXXXXXX`** (random address) with manufacturer data company 0x0000, value `0000`. It advertises no service UUIDs.
- The tester identifies this unit as the V100. The device does not report "V100" anywhere.
- `bikectl inspect` connected read-only without pairing prompts. No writes.

### Button events on FEA1 (observed)

In capture `ride2-v100-fea1.jsonl` the tester, while pedalling, pressed + five times, then − five times, and repeated the sequence. The capture holds 75 frames in alternating groups of five: 8 groups of + and 7 groups of −. Presses within a group were about 0.5–0.7 s apart.

| Button | Frame | Notes |
| --- | --- | --- |
| + (shift up) | `f3 05 03 01 fc` | corrected 2026-10-17, see below |
| − (shift down) | `f3 05 03 00 fb` | corrected 2026-10-17, see below |

**Correction (2026-10-17, later capture `plus.jsonl`, local):** the tester pressed only the button printed "+", in groups of five; all 12 captured frames were `f3050301fc`. The group labels of `ride2-v100-fea1.jsonl` were therefore swapped. The earlier swap of the mapping "for MyWhoosh" already matched this, so behaviour is unchanged: "+" emits shift_up, a harder gear in OsmolControl gears.

- Each press produced exactly one notification. There are no separate press/release frames and no counters. The project's exact-byte `PacketMap` model therefore fits; no stateful driver is needed for clicks.
- *Inferred:* the last byte is the 8-bit sum of the preceding bytes (`f3+05+03+00 = fb`), byte 1 looks like a length/type and byte 3 is the button code. Only codes 00/01 have been observed.
- **Untested:** holding a button (repeat or long-press frames?), pressing both buttons, very fast presses, reconnect behaviour, and whether FD09 carries anything.
- The V100 does **not** report a gear. Gear state, if any, must come from MyWhoosh or be labelled application state.

### Mapping run 2026-10-17 00:31 (`ride3-v100-mapping.jsonl`), unexplained

`bikectl monitor` with `v100.local.json`, 60 s. Requested sequence: + ×3, − ×3, hold + about 3 s, hold − about 3 s. Observed (seconds from connect):

| t | Frame | Action emitted |
| --- | --- | --- |
| 7.43 | `f3050300fb` | shift_up |
| 21.60 | `f3050301fc` | shift_down |
| 21.61 | `f3050300fb` | shift_up (10 ms after the previous frame) |
| 36.0 | link dropped | `disconnected` |
| 44.3 | automatic reconnect | `connected` |
| 47.78 | `f3050301fc` | shift_down |
| 52.73 | `f3050300fb` | shift_up |

- The software side behaved as designed: each matched frame emitted exactly one action, no unknown frame produced an action, and the bounded retry reconnected without a stale replay.
- The device side does not match the requested 6 clicks + 2 holds: only 5 frames arrived, and the link dropped once.
- **Tester report:** the tester held + and − together, and is certain that this caused the disconnect at 36 s. So *holding both buttons drops the BLE link* (tester-reported, consistent with the capture; whether it is a power-off/re-pair gesture is unknown). The app recovered by automatic reconnect. The near-simultaneous −/+ frames at 21.6 s are consistent with both buttons being pressed together (*inferred*).
- Still unresolved: why fewer single clicks arrived than planned, and whether a single-button hold emits repeats. No repeat frames were seen.

Local mapping: `v100.local.json` (git-ignored; README format). Regression test: `bike-core` `captured_v100_clicks`.

No VS200 assumptions were used; this mapping comes only from the capture above.

### Live controller → OpenBikeControl stand-in (2026-10-17 00:36, local capture)

a test script: V100 → `dist/bikectl connect-mywhoosh --no-mdns --controller … --mapping v100.local.json` → local synthetic TCP peer on 192.168.1.10 (not MyWhoosh). User pressed exactly + ×3, then − ×3, about 1 s apart.

| Peer t (s) | Received | Meaning |
| --- | --- | --- |
| 0.0 | `02ff00` | status: battery unknown, not ready |
| 4.06 | `02ff01` | status: ready (V100 connected) |
| 4.96 | `010201` `010200` | shift down press + release |
| 6.91, 7.96, 8.94 | `010101` `010100` each | shift up press + release (×3, 1 s apart) |
| 30.0, 60.0 | `02ff01` | 30 s status refresh |

- **Software path verified with real hardware input:** every FEA1 frame became exactly one press/release pair on the wire, the readiness status followed the BLE link, and the 30 s status refresh was sent. No unmapped frame produced an action.
- **Device delivery anomaly (repeat of the 00:31 run):** 6 presses gave only 4 frames. All three + presses arrived, but there was only one −, and it came *before* the + presses, about 1 s after subscription. In the 00:31 run the first frame after reconnect was also `…01fc` (−). Unresolved hypotheses: (a) the V100 re-sends its last event on (re)subscription and drops subsequent − presses; (b) presses are lost over the air; (c) `monitor` also subscribes Battery 2A19, unlike the fully successful `capture` run (ride2, FEA1 only, all 75 presses delivered). `btmon` needs CAP_NET_RAW (not available to the tester without sudo), so over-the-air confirmation was not possible.

### Direction in MyWhoosh (2026-10-17)

With the direct mapping (physical + → OpenBikeControl 0x01 "Shift Up / increase virtual gear"), the tester reported that MyWhoosh 5.7.0 shifted in the opposite direction from the one intended. The local mapping was swapped (+ `f3050300fb` → shift_down, − `f3050301fc` → shift_up). The raw button identities above are unchanged; only the tester-facing direction preference changed. Confirmed after the swap: the tester reports correct direction in MyWhoosh (`mywhoosh-live-3.log`: 83 actions, no V100 disconnects).
